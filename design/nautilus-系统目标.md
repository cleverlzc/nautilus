# Nautilus 系统目标

> 视角：企业架构理论（Enterprise Architecture，TOGAF 四域） + 生产系统约束理论（Theory of Constraints，Goldratt）
> 基线：v1 实现（378 行 Python，4 工具：read_file / write_file / edit_file / bash，单 ReAct 循环）
> 日期：2026-09-01

---

## 一、系统本体：Nautilus 是什么

Nautilus 是一个面向软件工程任务的 coding agent。它的不可约本质由第一性原理分解为五个组件：

| 组件 | 第一性问题 | v1 落地 |
|------|-----------|---------|
| ① LLM（认知） | 规则引擎无法理解意图与推理 | OpenAI 兼容 API（`llm.py`，19 行） |
| ② Tools（行动） | LLM 输出只是 token，碰不到文件系统 | 4 工具：read/write/edit/bash（`tools.py`，189 行） |
| ③ Loop（自主） | 单次 LLM→tool→done 是函数不是 agent | ReAct 循环（`agent.py`，81 行） |
| ④ Context（记忆） | LLM 无状态，每次调用失忆 | `messages` 数组，全量历史 |
| ⑤ Interface（I/O） | 没有输入通道，agent 收不到任务 | CLI argparse（`__main__.py`，68 行） |

核心循环（`agent.py:43-81`）就是 ReAct 原子的工程化：

```python
for i in range(max_iter):
    response = client.chat.completions.create(model, messages, tools=TOOL_SCHEMAS)
    message = response.choices[0].message
    if not message.tool_calls:
        print(message.content); return        # 终止：最终回答
    messages.append(message)                   # 思考回灌
    for call in message.tool_calls:
        result = execute_tool(call)            # 行动
        messages.append({"role": "tool", ...}) # 观察回灌
```

名称隐喻：鹦鹉螺的对数螺旋（logarithmic spiral）对应 ReAct 循环的螺旋逼近——每一圈 Thought→Action→Observation 不是原地打转，而是基于上一轮观察修正认知，朝答案收敛。自相似性（分形）意味着单个 ReAct 循环可封装为原子模块，嵌套调用即得多智能体协作的理论基础。

## 二、企业架构视角的系统目标

企业架构理论（TOGAF）将系统目标分解到四个架构域，自上而下回答"为什么存在"。Nautilus 的四域目标如下。

### 2.1 业务架构目标（Business Architecture）

业务架构回答"为谁创造什么价值"。

| 业务目标 | 含义 | v1 验收信号 |
|---------|------|------------|
| 自动化软件工程体力活 | 把"读文件→理解→改→跑测试→报告"这个闭环从人手交给机器 | 能在真实 repo 完成该闭环 |
| 释放开发者高阶时间 | 让人去做设计、判断、架构决策，机器做机械修改 | 任务摘要输出（`prompts.py` 第 6 条准则） |
| 降低编码任务交付延迟 | 从收到任务到产出可验证结果的时间 < 人手 | 单任务在 max_iter=20 内收敛 |
| 可审计的执行轨迹 | 每一步行动可追溯，便于人类事后复核 | 终端打印 `🔧 工具名(参数)` + 截断结果 |

业务目标的第一性推导：人手做编码任务的瓶颈不是"手指速度"，而是"上下文切换成本"——人需要重新进入某个文件的心智模型才能改一行。LLM 不存在这个切换成本，因此 agent 的业务价值 = 把高频低阶的上下文切换工作吸收掉。

### 2.2 数据架构目标（Data Architecture）

数据架构回答"信息如何流动与持久化"。

| 数据资产 | 形态 | v1 处理 | 目标 |
|---------|------|--------|------|
| 对话上下文（messages） | `[{role, content}]` 数组 | 全量保存在内存 | 在 context window 内最大化信息密度 |
| 工具观察结果 | 字符串 | 截断到 2000 字符显示，全量回灌 LLM | 不丢失决策关键信息，不爆 token |
| 文件系统状态 | 真实文件 | read/write/edit 直接操作磁盘 | agent 的行动对真实世界有副作用，可验证 |
| 命令执行结果 | stdout+stderr+exit code | 30s 超时捕获 | 提供可机读的成败信号 |

数据架构目标的核心张力：**上下文丰富 vs token 成本**。v1 选择全量历史（最简实现），设 max_iter=20 作为硬上限兜底。这意味着 v1 的数据目标不是"最优信息管理"，而是"保证闭环可跑通，为 v2 的压缩/子 agent 隔离提供基线"。

### 2.3 应用架构目标（Application Architecture）

应用架构回答"软件如何组织以实现业务目标"。

Nautilus 的应用架构是一个**单进程、单线程、同步的 ReAct 循环**，外接四个工具和一个 LLM API。目标分解：

| 应用目标 | 设计决策 | 理由 |
|---------|---------|------|
| 最小可运行本质 | ~378 行表达 agent 循环本质 | 验证设计后再迁移 TS/Rust；Aider 全量也才几千行 |
| 工具粒度粗起步 | read+write+edit+bash 四件套 | 覆盖感知（read）+行动（write/edit/bash）最小集 |
| 安全模型分阶段 | v1 全自动+日志，不加审批 | 学习阶段不需要 permission prompt；v2 再加 |
| 循环终止双保险 | LLM 不调工具=结束 + max_iter 兜底 | OpenAI tool calling 原生语义 + 防死循环 |
| 错误不崩溃 | 工具失败返回错误字符串，回灌 LLM 自纠 | `execute_tool` 把异常翻译成 observation |

应用架构的关键洞察：**agent 的本质不在单个组件的强度，而在组合方式**。Claude Code 的 43 个工具 vs Nautilus 的 4 个，区别不在数量，而在循环控制策略和上下文管理策略。v1 用最简组合验证这一点。

### 2.4 技术架构目标（Technology Architecture）

技术架构回答"用什么技术栈承载应用"。

| 技术决策 | 选择 | 理由 |
|---------|------|------|
| 语言 | Python 3.10+ | 最少代码量表达循环本质；Aider/OpenHands 路线 |
| LLM 接入 | OpenAI 兼容 API（`openai` SDK） | 协议事实标准，可接 qwen-plus 等兼容端点 |
| 工具执行 | `subprocess.run` + 30s 超时 | 直接 shell，无沙箱；v2 加 Docker 隔离 |
| 交互 | CLI（argparse） | 最小输入通道，支持管道 |
| 依赖 | 仅 `openai>=1.0.0` | 依赖越少，越易复现 |

技术架构目标：**用最薄的依赖栈跑通 agent 本质**。v1 不引入 rich（终端美化）、不引入 docker（沙箱）、不引入 MCP SDK（扩展协议）——这些都是 v2+ 的工程化层。

## 三、生产系统约束理论视角的系统目标

Goldratt 的约束理论（Theory of Constraints, ToC）认为：**任何系统的产出由其最薄弱的约束（瓶颈）决定**。系统目标不是"什么都做好"，而是"持续识别并打破约束，让有效产出最大化"。

### 3.1 系统目标的三元定义

ToC 对生产系统目标的标准定义是三元组——同时提升有效产出、降低库存、降低运行费用。映射到 Nautilus：

| ToC 维度 | 制造系统原义 | Nautilus 映射 | v1 现状 |
|---------|------------|-------------|---------|
| **有效产出（Throughput, T）** | 系统通过销售产生金钱的速率 | agent 正确完成编码任务（通过验证、符合用户意图）的速率 | 单任务串行，无并发 |
| **库存（Inventory, I）** | 投资在待售物上的钱 | 在途工作：已消耗的 token、未完成的工具调用、半成品上下文 | 全量历史累积，max_iter=20 截断 |
| **运行费用（Operational Expense, OE）** | 把库存转成产出所花的钱 | API token 成本 + 计算/等待时间 + 开发者监督/复核时间 | 无审批，监督成本≈0；token 成本随历史线性增长 |

**Nautilus 的系统目标（ToC 陈述）**：

> 在保证任务正确性的前提下，最大化单位时间正确完成的编码任务数（提升 T），同时压缩在途 token 与半成品上下文（降低 I），并最小化 API 成本与人类监督时间（降低 OE）。

关键推论：**单纯让 LLM 更快不等于系统更好**。如果工具执行慢、上下文管理差导致 LLM 反复试错，那么 LLM 速度提升会被库存（浪费的 token）吃掉。系统的优化必须服从瓶颈，不能局部优化非瓶颈环节。

### 3.2 约束识别（五大聚焦步骤之 Step 1）

Nautilus v1 的约束链分析：

| 环节 | 是否瓶颈 | 证据 |
|------|---------|------|
| LLM 推理调用 | **是，主瓶颈** | 每个 ReAct 圈必须经过一次 LLM 调用；决策质量决定整圈成败 |
| Context window 容量 | **是，次瓶颈** | 全量历史累积，长任务会在 ~max_iter 内撑爆窗口 |
| 工具执行速度 | 否 | read/write 是本地 IO，bash 30s 超时，相对 LLM 秒级响应可忽略 |
| CLI 解析 | 否 | 一次性，不进入循环 |
| 人类监督 | 否（v1） | 全自动无审批，不构成瓶颈；v2 加审批后可能成为新瓶颈 |

**v1 的约束结论**：LLM 调用是系统的鼓（Drum）。整个系统的节奏由 LLM 的响应时间决定。所有其他环节必须服从这个节奏——工具要快、上下文要精炼，不能让 LLM 等待或拿到垃圾上下文。

### 3.3 挖尽约束（Step 2：Exploit the constraint）

既然 LLM 是瓶颈，就要让每一次 LLM 调用产出最大化决策价值。Nautilus 的对应设计：

| 挖尽手段 | v1 实现 | 机制位置 |
|---------|--------|---------|
| 好的系统提示词 | 6 条行为准则（先读后改、最小修改、遵循风格、改完验证、专注、给摘要） | `prompts.py` |
| 工具 schema 清晰 | 每个工具有 description，参数有 type 约束 | `tools.py:9-90` |
| 工具失败翻译成 observation | 异常返回字符串而非抛出 | `tools.py` 各工具的 except 分支 |
| 一次只做一件事 | 提示词第 5 条禁止并行调用塞满 | `prompts.py` |
| 截断显示但不截断回灌 | 终端 2000 字符截断，回灌 LLM 用全量 | `agent.py:8-12, 71` |

挖尽约束的本质：**不让 LLM 把时间浪费在低质量输入上**。坏的工具描述、坏的错误处理会让 LLM 反复试错，等于在瓶颈处制造废品。

### 3.4 服从约束（Step 3：Subordinate everything else）

非瓶颈环节必须服从瓶颈节奏。Nautilus 的服从设计：

| 非瓶颈环节 | 服从方式 |
|-----------|---------|
| 工具执行 | 同步阻塞，结果立即可用于下一圈 LLM；不让 LLM 等 |
| 上下文管理 | 全量回灌，保证 LLM 拿到完整信息做决策 |
| 错误处理 | 工具错误也回灌，让 LLM 自己决定纠错路径 |
| 循环终止 | LLM 不调工具即结束——决策权交给瓶颈本身 |
| max_iter | 兜底防死循环，但默认 20 给足 LLM 收敛空间 |

服从约束的反面：v1 没有 streaming、没有并行工具调用、没有子 agent——这些都会引入异步复杂度，在瓶颈未打破前是局部优化，反而增加库存（在途 token）而不提升产出。

### 3.5 打破约束（Step 4：Elevate the constraint）

当挖尽与服从都到极限，必须投入资源打破瓶颈本身。Nautilus 的演进路线对应打破手段：

| 打破手段 | 对应 v 版本 | 效果 |
|---------|-----------|------|
| 换更强/更快的模型 | 任意版本可切换 `--model` | 提升单圈决策质量与速度 |
| 上下文压缩 | v2 | 解放次瓶颈（context window） |
| 子 agent 隔离 | v3 | 把长任务的上下文从主循环隔离 |
| 流式输出 | v2 | 降低用户感知延迟（不提升 T，但降 OE 中的监督时间） |
| 精细工具拆分（Grep/Glob 独立） | v2 | 让 LLM 用更少 token 表达意图，单圈更高效 |
| 权限审批 | v2 | 引入人类监督，可能成为新瓶颈，需配套异步通知 |
| MCP 协议 + Skills | v3+ | 扩展工具集，但工具数增加不打破 LLM 瓶颈，只挖尽它 |

### 3.6 循环重复（Step 5：Repeat）

ToC 的关键警告：**打破一个瓶颈后，新的瓶颈会出现，不能让惯性阻止继续改进**。

Nautilus 的约束迁移预测：

- v1 瓶颈：LLM 调用 + context window
- v2 打破 context window（压缩+子 agent）后，新瓶颈可能是 → 工具执行（bash 30s 超时）或 → 人类审批
- v3 打破人类审批（异步通知+批量复核）后，新瓶颈可能是 → 多 agent 协调开销或 → API 成本

每一轮都必须重新识别瓶颈，不能假设 v1 的瓶颈永远是瓶颈。

### 3.7 鼓-缓冲-绳（Drum-Buffer-Rope）在 Nautilus 的映射

Goldratt 的 DBR 排程法映射到 agent 循环：

| DBR 元素 | 制造系统原义 | Nautilus 映射 |
|---------|------------|-------------|
| **鼓（Drum）** | 瓶颈工序的节拍决定全厂节奏 | LLM 一次调用 = 一拍；ReAct 圈数 = 节拍数 |
| **缓冲（Buffer）** | 在瓶颈前备料，保证瓶颈不饿 | `messages` 上下文 = 信息缓冲；要够大让 LLM 有决策依据，但不能撑爆窗口 |
| **绳（Rope）** | 限制投料速率，不让在途库存爆 | `max_iter` = 绳长；超过即终止，防止 token 库存无限膨胀 |

DBR 的核心洞察对 Nautilus 的指导：**不要无限增加 max_iter**。max_iter 是绳，它的作用是限制在途库存（已花掉的 token 但未产出正确结果的工作）。绳子放得太长，库存爆炸，运行费用（OE）随之爆炸，而有效产出（T）并不提升——因为瓶颈还是那个 LLM，它一拍只能处理一拍的工作。

## 四、两理论的交汇：Nautilus 的综合系统目标

企业架构理论回答"系统该做什么"（What），约束理论回答"系统该如何持续最优"（How to optimize）。两者交汇，Nautilus 的系统目标可一句话陈述：

> **Nautilus 的目标是：以最小依赖栈（技术架构）承载 ReAct 循环（应用架构），把编码任务的上下文切换体力活从人手吸收到机器（业务架构），同时持续识别并打破 LLM 这个瓶颈（约束理论），使正确完成的编码任务有效产出最大化，而在途 token 库存与 API+监督运行费用最小化。**

这个目标分解为可验证的 v1 子目标：

| 子目标 | 验收标准 | v1 是否达成 |
|--------|---------|-----------|
| 闭环可跑通 | 能完成"读→改→跑测试→报告" | ✅ 已验证（实现总结记录） |
| agent 本质清晰 | ~378 行表达 ReAct 原子 | ✅ 比目标 200 行略多（工具 schema 占行） |
| 瓶颈可识别 | LLM 调用为鼓，max_iter 为绳 | ✅ 架构清晰 |
| 错误不崩溃 | 工具失败回灌 observation | ✅ 各 except 分支 |
| 决策可审计 | 终端打印每步工具调用 | ✅ `_print_tool_call` |
| 安全暂留白 | 全自动无审批（v2 再补） | ✅ 显式设计决策 |

v2+ 的未达目标（约束理论视角的下一步）：

- 上下文压缩（打破次瓶颈 context window）
- 子 agent 隔离（把长任务库存从主循环剥离）
- 权限审批（引入人类监督，需配套防新瓶颈）
- 精细工具拆分（Grep/Glob 独立，挖尽 LLM 瓶颈）
- 流式输出（降低监督 OE）

## 五、附录：约束理论五大聚焦步骤速查

| 步骤 | 动作 | Nautilus 对应 |
|------|------|-------------|
| 1. 识别约束 | 找到瓶颈工序 | LLM 调用 + context window |
| 2. 挖尽约束 | 让瓶颈满负荷高质量运转 | 好提示词 + 清晰 schema + 错误回灌 |
| 3. 服从约束 | 非瓶颈环节配合瓶颈节奏 | 同步工具、全量回灌、不引入异步复杂度 |
| 4. 打破约束 | 投入资源提升瓶颈本身 | 换模型 / 压缩上下文 / 子 agent |
| 5. 循环重复 | 警惕惯性，重新识别新瓶颈 | v2 后瓶颈迁移到工具执行或人类审批 |
