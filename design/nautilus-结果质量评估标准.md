# Nautilus 结果质量评估标准

> 参考框架：Hermes 评估器三维模型（过程精准度 / 简洁度 / 结果质量）
> 基线：Nautilus v1（378 行 Python，4 工具，ReAct 循环，max_iter=20）
> 日期：2026-09-03

---

## 一、参考来源：Hermes 评估器

Hermes-Agent（Nous Research，2026-02 发布）引入了 Meta-Agent 自主进化能力，其核心是通过 GEPA 算法总结反思历史任务轨迹，优化 Skill 知识。华为云核心网 AI Lab 在《Skill自进化技术洞察及产品落地实践》中，将 Hermes 的评估器精细化定义为三个维度，量化衡量 Skill 自进化的质量：

| 维度 | Hermes 原义 | 核心问题 |
|------|-----------|---------|
| **结果质量** | Skill 执行后产出的最终结果是否正确、是否达成任务目标 | 做对了吗？ |
| **过程精准度** | Skill 执行过程中每一步是否精准——工具选择是否合理、步骤是否必要、错误是否自纠 | 走对路了吗？ |
| **简洁度** | Skill 执行是否经济——步骤数、token 消耗、冗余操作是否最小化 | 走得够短吗？ |

三者的关系不是独立叠加，而是**有优先级的递进**：结果质量是门槛（做不对一切归零），过程精准度是质量（做对了但路走歪也有损耗），简洁度是效率（路对了但太长浪费资源）。Hermes 用这三个维度构成评估闭环——总结成功与失败的历史轨迹，迭代优化合并，通过 GEPA 进化树不断产生更高质量的 Skill。

Nautilus 作为一个 coding agent（而非 Skill 自进化系统），需要适配这三个维度：评估对象从"Skill 自进化质量"变为"单次编码任务执行质量"。但三维骨架不变。

---

## 二、评估框架总览

### 2.1 评估对象

一次 Nautilus 任务执行 = 从 CLI 接收 prompt 到 agent 循环终止（LLM 给出最终回答 / 达到 max_iter）的完整过程。

评估的输入：
- 用户 prompt（任务描述）
- 执行前的文件系统快照
- 执行后的文件系统快照
- 完整的 ReAct 轨迹（每一圈的 thinking → tool_call → observation）
- 最终回答文本

### 2.2 三维评估模型

```
                         ┌──────────────┐
                    ┌───→│  D1 正确性    │  门槛层：做对了吗？
                    │    └──────────────┘
                    │    ┌──────────────┐
  Nautilus 任务执行 ├─────→│ D2 过程精准度 │  质量层：走对路了吗？
                    │    └──────────────┘
                    │    ┌──────────────┐
                    └───→│  D3 简洁度    │  效率层：走得够短吗？
                         └──────────────┘
```

### 2.3 评分体系

每个维度采用 5 分制（0-4），含义如下：

| 分值 | 含义 | 信号 |
|------|------|------|
| 4 | 优秀 | 该维度无可改进 |
| 3 | 良好 | 有微小瑕疵但不影响整体质量 |
| 2 | 及格 | 有明显问题但任务基本完成 |
| 1 | 不及格 | 该维度有严重缺陷 |
| 0 | 失败 | 该维度完全未达到要求 |

**总分 = D1 × 0.5 + D2 × 0.3 + D3 × 0.2**（权重反映优先级递进：正确性 > 过程 > 简洁度）

总分 ≥ 3.0 视为合格交付。

## 三、D1：正确性（结果质量）

### 3.1 定义

Nautilus 执行任务后，**产出物是否正确达成了用户 prompt 描述的意图**。这是门槛维度——结果错了，过程再优雅、步骤再简洁也归零。

### 3.2 评估项

D1 分解为 4 个子项，每个子项独立评分后取加权平均。

#### D1.1 任务完成度

| 分值 | 标准 |
|------|------|
| 4 | 任务意图完全达成，产出物可直接使用 |
| 3 | 任务核心目标达成，有微小遗漏但不影响使用 |
| 2 | 任务部分完成，关键功能缺失但框架在 |
| 1 | 任务基本未完成，产出物不可用 |
| 0 | 完全没有产出或产出物与任务无关 |

判断依据：对比用户 prompt 的显式意图与执行后的文件系统状态 / 命令输出。

示例：
- prompt = "创建一个 hello.py，运行它，确认输出 hello world"
- 4 分：hello.py 存在 + 内容正确 + bash 执行输出 "hello world" + agent 报告确认
- 2 分：hello.py 存在但内容不对 / 未运行验证
- 0 分：文件未创建

#### D1.2 代码正确性

| 分值 | 标准 |
|------|------|
| 4 | 代码语法正确 + 逻辑正确 + 通过已有测试 |
| 3 | 代码语法正确 + 逻辑正确，但未跑测试或测试未覆盖 |
| 2 | 代码语法正确但逻辑有缺陷 |
| 1 | 代码有语法错误但可修复 |
| 0 | 代码完全不可运行 |

判断依据：
- `bash` 工具的 exit code（`tools.py:161`：`[exit code: 0]` = 成功）
- `bash` 工具的 stdout/stderr 输出
- 文件内容审查（`read_file` 观察回灌的结果）

关键约束：Nautilus 的系统提示词第 4 条要求"改完验证"（`prompts.py:9`），因此**是否跑了测试是 D1.2 的重要信号**。如果 agent 修改了代码但未运行任何验证命令，D1.2 上限为 3。

#### D1.3 文件系统状态正确性

| 分值 | 标准 |
|------|------|
| 4 | 只改了该改的文件，未碰不该碰的文件 |
| 3 | 改对了目标文件，但有微小的误改（如多加空行） |
| 2 | 改对了主要文件但误改了其他文件 |
| 1 | 创建/修改了不该动的文件 |
| 0 | 破坏性修改（删除了不该删的文件等） |

判断依据：执行前后文件系统 diff。

关键约束：系统提示词第 2 条要求"最小修改"（`prompts.py:7`）。`edit_file` 工具（`tools.py:118-144`）要求 old_string 精确匹配且唯一，多处匹配会报错——这个机制本身是正确性的保障，评估时应检查 agent 是否优先用 `edit_file` 而非 `write_file` 做局部修改。

#### D1.4 最终回答准确性

| 分值 | 标准 |
|------|------|
| 4 | 最终回答准确描述了做了什么、结果如何 |
| 3 | 最终回答基本准确，有微小遗漏 |
| 2 | 最终回答与实际执行有出入 |
| 1 | 最终回答误导性描述 |
| 0 | 无最终回答（达到 max_iter 截断） |

判断依据：系统提示词第 6 条要求"完成后给摘要"（`prompts.py:10`）。最终回答是 agent 最后一轮不包含 tool_calls 的 `message.content`（`agent.py:52-55`）。

特殊情形：如果 agent 达到 max_iter 被强制终止（`agent.py:81`：打印 ⚠️ 警告），D1.4 直接为 0 分——因为不存在"最终回答"。

### 3.3 D1 综合评分

**D1 = D1.1 × 0.35 + D1.2 × 0.30 + D1.3 × 0.20 + D1.4 × 0.15**

权重逻辑：任务完成度最重要（35%），代码正确性次之（30%），文件系统状态再次（20%），最终回答权重最低（15%）——因为前三个对了，回答基本不会差。

### 3.4 D1 一票否决规则

以下情形 D1 直接归 0，不再逐项评分：
- 文件系统破坏性修改（删除了不该删的文件）
- `bash` 执行了危险命令导致环境损坏（非预期 rm -rf 等）
- 达到 max_iter 截断且无任何有效产出

## 四、D2：过程精准度

### 4.1 定义

Nautilus 在 ReAct 循环中，**每一步行动是否精准合理**——工具选择是否正确、执行顺序是否合逻辑、遇到错误是否自纠、有无无效操作。这是质量维度——即使结果对了，过程混乱也说明稳定性差，换一个任务可能就做不对。

### 4.2 评估项

D2 分解为 4 个子项。

#### D2.1 先读后改（Read-before-Modify）

| 分值 | 标准 |
|------|------|
| 4 | 每次修改文件前都先 read_file 读取了目标文件 |
| 3 | 绝大多数修改前有读取，偶尔遗漏 |
| 2 | 有时直接写文件但不影响结果 |
| 1 | 经常不读就改 |
| 0 | 从不读取直接修改 |

依据：系统提示词第 1 条"先读后改"（`prompts.py:6`）。

检查方法：遍历 ReAct 轨迹，对每个 `write_file` 或 `edit_file` 调用，检查其前面是否有对同一 path 的 `read_file` 调用。

#### D2.2 工具选择精准度

| 分值 | 标准 |
|------|------|
| 4 | 每次都选了最合适的工具（局部修改用 edit_file，新建用 write_file，搜索用 bash） |
| 3 | 工具选择基本合理，偶尔次优（如用 write_file 整文件重写做局部修改） |
| 2 | 多次用错工具但最终结果可接受 |
| 1 | 工具选择严重不当 |
| 0 | 工具选择完全混乱 |

依据：Nautilus 有 4 个工具（`tools.py`），各有适用场景：
- `read_file`：读取 utf-8 文本文件
- `write_file`：新建文件或整文件重写
- `edit_file`：精确局部修改（`tools.py:118`：要求 old_string 精确匹配且唯一）
- `bash`：执行 shell 命令

典型错误：
- 用 `write_file` 重写整个文件只为改一行 → 应该用 `edit_file`
- 用 `bash "cat file"` 读取文件 → 应该用 `read_file`
- 用 `bash "echo ... > file"` 写文件 → 应该用 `write_file`

#### D2.3 错误自纠能力

| 分值 | 标准 |
|------|------|
| 4 | 遇到工具错误后立即理解原因并修正路径 |
| 3 | 遇到错误后有一次试错但很快修正 |
| 2 | 遇到错误后多次试错才修正 |
| 1 | 遇到错误后反复重试相同方法 |
| 0 | 遇到错误后陷入死循环或放弃 |

依据：Nautilus 的工具错误处理策略是"返回错误字符串作为 observation 回灌 LLM"（`tools.py` 各 except 分支 + `agent.py:73-79`）。这意味着 LLM 有机会从错误中学习并自纠。

典型错误信号（来自 `tools.py`）：
- `edit_file` 返回"找到 N 处匹配" → agent 应提供更多上下文
- `edit_file` 返回"找不到要替换的文本" → agent 应先 read_file 确认内容
- `bash` 返回 exit code 非 0 → agent 应理解 stderr 并修正
- `read_file` 返回"文件不存在" → agent 应检查路径

#### D2.4 验证闭环

| 分值 | 标准 |
|------|------|
| 4 | 修改代码后主动运行测试/构建命令验证 |
| 3 | 修改后运行了部分验证但不完整 |
| 2 | 修改后仅做了简单检查（如 import） |
| 1 | 修改后未做任何验证 |
| 0 | 修改后未验证且最终回答声称"已完成" |

依据：系统提示词第 4 条"改完验证"（`prompts.py:9`）。这是过程精准度的关键信号——agent 是否在"修改"和"报告完成"之间插入了"验证"步骤。

### 4.3 D2 综合评分

**D2 = D2.1 × 0.20 + D2.2 × 0.25 + D2.3 × 0.30 + D2.4 × 0.25**

权重逻辑：错误自纠能力权重最高（30%），因为它是 agent 区别于"单次函数调用"的核心价值——ReAct 循环的意义就在于能从 observation 中调整策略。验证闭环和工具选择各 25%，先读后改 20%。

## 五、D3：简洁度

### 5.1 定义

Nautilus 在达成正确结果的前提下，**所消耗的步骤数和资源是否最小化**。这是效率维度——结果对了、过程也对，但如果用 15 圈循环完成本可以 3 圈完成的任务，就是资源浪费。

### 5.2 评估项

D3 分解为 3 个子项。

#### D3.1 迭代效率

| 分值 | 标准 |
|------|------|
| 4 | ReAct 循环圈数 ≤ 理论最小圈数 × 1.5 |
| 3 | 圈数 ≤ 理论最小圈数 × 2.0 |
| 2 | 圈数 ≤ 理论最小圈数 × 3.0 |
| 1 | 圈数 > 理论最小圈数 × 3.0 |
| 0 | 达到 max_iter（20）被强制截断 |

"理论最小圈数"定义：一个理想的 agent 完成该任务所需的最少 ReAct 圈数。例如：
- "创建 hello.py 并运行" → 理论最小 2 圈（write_file + bash）
- "读取 X 文件，修复 Y bug，跑测试" → 理论最小 3-4 圈（read + edit + bash）

依据：`agent.py:43` 的 `for i in range(max_iter)` 循环。max_iter=20 是"绳"（ToC 框架中的 Rope），限制在途库存（token 消耗）。达到 max_iter 意味着绳子用尽，D3.1 直接归 0。

#### D3.2 工具调用有效性

| 分值 | 标准 |
|------|------|
| 4 | 无冗余工具调用（每次调用都产出有效信息） |
| 3 | ≤ 1 次冗余调用（如重复读取已读过的文件） |
| 2 | 2-3 次冗余调用 |
| 1 | > 3 次冗余调用 |
| 0 | 大量冗余调用，超过总调用数一半 |

冗余调用的判定：
- 重复 `read_file` 同一路径（内容未变化的情况下）
- `bash` 执行相同命令
- `edit_file` 用空 new_string 或 old_string == new_string
- 对同一文件连续多次 `write_file`（每次覆盖上一次）

#### D3.3 上下文经济性

| 分值 | 标准 |
|------|------|
| 4 | 每条 message 都贡献了有效信息，无垃圾 observation |
| 3 | 有少量无效信息回灌但不显著影响效率 |
| 2 | 有明显的无效信息（如长 bash 输出未截断） |
| 1 | 大量无效信息回灌，严重占用 context window |
| 0 | context window 被无效信息撑满导致任务失败 |

依据：Nautilus v1 的上下文管理策略是"全量历史"（设计文档明确选择），`_truncate` 函数（`agent.py:8-12`）只截断终端显示（2000 字符），**回灌 LLM 的是全量 result**（`agent.py:73-79`）。这意味着：
- 长 bash 输出会全量进入 messages，消耗 token
- 长 read_file 结果同样全量回灌
- 评估时应检查是否有可以避免的大输出

### 5.3 D3 综合评分

**D3 = D3.1 × 0.40 + D3.2 × 0.35 + D3.3 × 0.25**

权重逻辑：迭代效率权重最高（40%），因为圈数直接决定 token 成本（ToC 框架中的运行费用 OE）。工具调用有效性次之（35%）。上下文经济性 25%——v1 的全量历史策略是已知的设计权衡，不应过度惩罚。

## 六、综合评分与等级

### 6.1 总分计算

```
总分 = D1 × 0.5 + D2 × 0.3 + D3 × 0.2
```

| 维度 | 权重 | 理由 |
|------|------|------|
| D1 正确性 | 50% | 结果不对一切归零——这是门槛层 |
| D2 过程精准度 | 30% | 结果对了但过程乱说明不可复现——这是质量层 |
| D3 简洁度 | 20% | 结果对、过程对但太慢是资源浪费——这是效率层 |

### 6.2 质量等级

| 总分 | 等级 | 含义 | 后续动作 |
|------|------|------|---------|
| ≥ 3.5 | A（优秀） | 交付质量高，可直接使用 | 记录为标杆轨迹 |
| 3.0 - 3.4 | B（合格） | 交付质量合格，有小瑕疵 | 记录问题点，可使用 |
| 2.0 - 2.9 | C（需改进） | 交付质量勉强，有明显问题 | 需人工复核后决定是否使用 |
| < 2.0 | D（不合格） | 交付质量不达标 | 不可使用，需重新执行或人工介入 |

### 6.3 最低门槛约束

即使总分 ≥ 3.0，以下任一条件触发则降级为 C（需改进）：
- D1 < 3（正确性不达标——结果有缺陷的交付不能评为 B 以上）
- D2.3 ≤ 1（错误自纠能力差——遇到错误反复重试说明 agent 稳定性不足）
- D3.1 = 0（达到 max_iter 截断——说明任务超出当前能力边界）

## 七、评估流程

### 7.1 评估执行步骤

```
Step 1: 准备
  ├── 记录执行前文件系统快照（git status / ls）
  ├── 记录执行前 git commit hash（如在 git 仓库中）
  └── 准备标准 prompt

Step 2: 执行
  ├── 运行 nautilus "prompt"
  ├── 完整保存终端输出（含 🔧 工具调用 + → 观察结果 + ✅ 最终回答）
  └── 记录执行后文件系统快照

Step 3: 提取 ReAct 轨迹
  ├── 从终端输出解析每次工具调用（按 🔧 标记分割）
  ├── 统计工具调用次数、圈数、各工具使用比例
  └── 提取最终回答（✅ 标记后的内容）

Step 4: 逐维评分
  ├── D1 正确性：对比 prompt 意图 vs 文件系统 diff + 最终回答
  ├── D2 过程精准度：审查 ReAct 轨迹的工具选择和执行顺序
  └── D3 简洁度：统计圈数、冗余调用、上下文体积

Step 5: 综合评分
  ├── 计算三维加权总分
  ├── 检查最低门槛约束
  └── 确定质量等级
```

每次评估记录为一个 JSON 条目：

## 八、标准评估用例

### 8.1 用例一：简单创建+验证

**Prompt**：`创建一个 hello.py，运行它，确认输出 hello world`

| 维度 | 理想轨迹 | 评分 |
|------|---------|------|
| D1 正确性 | hello.py 存在 + 内容正确 + bash 输出 hello world + 回答确认 | D1=4 |
| D2 过程精准度 | write_file→bash 一步到位，无需 read（新建文件不先读合理） | D2=3.5 |
| D3 简洁度 | 理论最小 2 圈（write + bash），实际 2-3 圈 | D3=4 |

### 8.2 用例二：Bug 修复闭环

**Prompt**：`修复 src/calculator.py 中的除法 bug，然后跑测试确认`

| 维度 | 理想轨迹 | 评分 |
|------|---------|------|
| D1 正确性 | bug 已修复 + 测试通过 + 回报修复内容 | D1=4 |
| D2 过程精准度 | read_file→edit_file→bash(python -m pytest)，每步精准 | D2=4 |
| D3 简洁度 | 理论最小 3 圈，实际 3-4 圈 | D3=4 |

### 8.3 用例三：反模式——用 write_file 整文件重写

**Prompt**：`修复 src/calculator.py 中的除法 bug`

**实际轨迹**：read_file → write_file（整文件重写，包含修复）

| 维度 | 分析 | 评分 |
|------|------|------|
| D1 正确性 | bug 可能修了，但 D1.3 文件系统状态正确性扣分（非最小修改） | D1=3.2 |
| D2 过程精准度 | D2.2 工具选择扣分（应用 edit_file 局部修改，而非 write_file 整文件重写） | D2=2.75 |
| D3 简洁度 | write_file 整文件内容消耗更多 token | D3=2.5 |

### 8.4 用例四：反模式——不验证就声称完成

**Prompt**：`修复 src/calculator.py 中的除法 bug`

**实际轨迹**：read_file → edit_file → ✅ "已修复"

| 维度 | 分析 | 评分 |
|------|------|------|
| D1 正确性 | D1.2 上限为 3（未跑测试） | D1=2.55 |
| D2 过程精准度 | D2.4 验证闭环 = 1（修改后未做任何验证） | D2=2.45 |
| D3 简洁度 | 圈数少但信息不足 | D3=3.0 |

### 8.5 用例五：反模式——达到 max_iter 截断

**Prompt**：复杂重构任务

**实际轨迹**：20 圈循环未收敛，打印 ⚠️ 警告

| 维度 | 分析 | 评分 |
|------|------|------|
| D1 正确性 | 无最终回答（D1.4=0），任务未完成 | D1≤1 |
| D2 过程精准度 | 可能 D2.3 错误自纠差（反复试错） | D2≤2 |
| D3 简洁度 | D3.1=0（达到 max_iter 截断） | D3≤1 |

## 九、评估结果的应用

### 9.1 用于 v1 验收

Nautilus v1 的验收标准（设计文档定义）：能在真实 repo 里完成"读取文件→理解→修改→跑测试→报告结果"闭环。

验收判据：
- 运行标准评估用例二（Bug 修复闭环）
- 总分 ≥ 3.0 且 D1 ≥ 3.0
- 若不达标，定位是 D1（结果错）、D2（过程乱）、还是 D3（太慢），针对性改进

### 9.2 用于 v2 演进决策

收集多次评估数据后，按维度统计低分频次：

| 低分频次最高的维度 | v2 优先改进方向 |
|------------------|---------------|
| D1.2 代码正确性低 | 改进系统提示词（强化验证要求）或换更强模型 |
| D2.2 工具选择差 | 拆出更细粒度工具（Grep/Glob 独立于 bash） |
| D2.3 错误自纠差 | 优化工具错误信息（更清晰的错误描述） |
| D3.1 迭代效率低 | 引入上下文压缩或子 agent 隔离 |
| D3.3 上下文经济性差 | 实现工具输出截断回灌（而非全量） |

### 9.3 用于与 Hermes 对齐的自进化闭环

Hermes 的评估器服务于 Skill 自进化：评估→总结轨迹→优化 Skill→再评估。Nautilus 当前无 Skill 自进化能力，但评估标准的建立是未来自进化的前提：

```
当前：人工评估 → 人工改进提示词/工具设计
v2：  自动评估（LLM-as-judge）→ 人工改进
v3：  自动评估 → 自动优化系统提示词（接近 Hermes 的 GEPA 路径）
```
