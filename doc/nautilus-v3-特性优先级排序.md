# Nautilus v3 特性优先级排序

## 排序框架

从两个维度评估每个特性：

1. **约束理论视角（架构师）**：打破当前哪个瓶颈？对有效产出（T）/库存（I）/运行费用（OE）的影响？
2. **工程视角（工程师）**：实现难度？对现有代码的侵入性？是否被其他特性依赖？

## v3 候选特性（9 个）

v3 设计文档定义的 5 个特性 + 审视报告发现的 4 个遗留问题 = 9 个候选：

| # | 特性 | 来源 | 约束理论影响 | 工程影响 | 依赖关系 |
|---|------|------|-------------|---------|---------|
| 1 | 上下文压缩 | 设计路线图 + 审视问题 3 | 打破次瓶颈（context window），降低库存（I） | 高侵入性（改 agent.py 核心循环） | 无依赖，被子 agent 依赖 |
| 2 | 子 agent（上下文隔离） | 设计路线图 | 打破 context window 瓶颈，隔离长任务库存 | 高侵入性（新增 agent 调度层） | 依赖上下文压缩 |
| 3 | plan mode | 设计路线图 | 提升有效产出（T）——先规划再执行减少无效迭代 | 中侵入性（新增 plan→execute 两阶段） | 无依赖 |
| 4 | MCP 协议 | 设计路线图 | 扩展工具集，不改瓶颈 | 高复杂度（协议实现） | 无依赖 |
| 5 | 记忆系统 | 设计路线图 | 跨会话上下文保持，降低 OE | 高复杂度（持久化+检索） | 无依赖 |
| 6 | Skills/插件 | 设计路线图 | 可复用工作流，降低 OE | 高复杂度（插件框架） | 依赖 MCP 或独立 |
| 7 | GBK 编码修复 | 审视问题 1 | 不改瓶颈，消除阻塞 | 极低（2 行代码） | 无依赖 |
| 8 | bash 危险命令过滤 | 审视问题 2 | 安全兜底，不改瓶颈 | 低（黑名单检查） | 无依赖 |
| 9 | edit_file 模糊匹配建议 | 审视问题 4 | 提升工具选择精准度（D2.2） | 低（失败时返回行号建议） | 无依赖 |

## 优先级排序（从高到低）

| 优先级 | 特性 | 理由 |
|--------|------|------|
| **P0** | **GBK 编码修复** | 2 行代码修复一个阻塞性 bug，投入产出比最高，不做会影响后续所有 E2E 测试体验 |
| **P0** | **bash 危险命令过滤** | 安全兜底，低投入高收益，`--approval` 已有审批门基础 |
| **P1** | **上下文压缩** | 打破当前最大次瓶颈（context window）。ToC 视角：直接降低库存（I）——长任务不再因历史膨胀失败。是子 agent 的前置依赖。当前截断只管单次工具结果，不管对话历史本身 |
| **P1** | **子 agent（上下文隔离）** | 打破 context window 瓶颈的另一手段——把长任务库存从主循环剥离。ToC 视角：降低主循环库存（I），提升有效产出（T）。依赖上下文压缩 |
| **P2** | **plan mode** | 先规划再执行，减少无效迭代。ToC 视角：提升有效产出（T）——减少 LLM 试错圈数。独立特性，不依赖压缩/子 agent |
| **P3** | **记忆系统** | 跨会话上下文保持。ToC 视角：降低运行费用（OE）——agent 不需要每次从零理解项目。高复杂度但高价值 |
| **P3** | **Skills/插件** | 可复用工作流。ToC 视角：降低 OE——沉淀经验复用。但依赖记忆系统或 MCP 做存储 |
| **P4** | **MCP 协议** | 扩展工具集的标准化接口。ToC 视角：不直接打破瓶颈，是扩展机制。高复杂度，ROI 低（当前 6 工具够用） |
| **P4** | **edit_file 模糊匹配建议** | 改进项，非阻塞。edit_file 失败时返回行号建议，帮助 LLM 提供更精确的 old_string |

## 排序逻辑

1. **先修 bug 再加功能**（P0）：GBK 编码和 bash 安全是阻塞性/安全性问题，投入极低，必须最先做。
2. **先打破最大瓶颈再加扩展**（P1）：context window 是 v2 后的最大约束（ToC 的次瓶颈）。上下文压缩和子 agent 直接打破这个约束，且子 agent 依赖压缩。
3. **先提升产出效率再加生态**（P2）：plan mode 直接减少 LLM 无效迭代（提升 T），独立且中等复杂度。
4. **记忆和 Skills 高价值但高复杂度**（P3）：跨会话记忆和可复用工作流是"产品级"特征，但实现复杂度高，放后。
5. **MCP 协议 ROI 最低**（P4）：当前 6 工具够用，MCP 是扩展机制而非核心能力，且协议实现复杂度高。

## 建议的实施顺序

```
P0: GBK 编码修复 → bash 危险命令过滤     （2 个小修，1 轮完成）
P1: 上下文压缩 → 子 agent               （2 个大特性，2 轮完成）
P2: plan mode                           （1 个中等特性，1 轮完成）
P3: 记忆系统 → Skills/插件              （2 个大特性，2 轮完成）
P4: MCP 协议 → edit_file 模糊匹配建议    （1 大 1 小，最后做）
```
